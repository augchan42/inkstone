## Findings

### [medium] Backend 3 availability rule contradicts its own tool restriction, and the "always available" fallback can disappear without saying what happens to the loop
**Where:** `skills/codex-review/reviewer-backends.md:21`, `skills/codex-review/reviewer-backends.md:232-238`, `skills/plan-review-loop/SKILL.md:110` · **Lane:** correctness / contracts

**Defect.** Line 232 makes context-blind subagents **Read/Glob/Grep only**, with no shell, write tools or delegation. Line 238 then says the backend is unavailable only "If **neither** restricted execution **nor** output capture is available". The table at line 21 says it is skipped when the host "cannot restrict tools **and** capture reviewer output". Read literally, both conditions let an executor use unrestricted subagents (for example general-purpose ones with Bash/Edit) whenever output capture works, which on Claude Code is always. That breaks the "reviewers may not edit reviewed source" guarantee in `SKILL.md:209-210`. Read strictly, the backend needs a read-only agent definition. Inkstone ships no `agents/` directory, so on a host with no Codex and no opencode, the last-resort backend may not exist at all. Before this change it was "fallback, always available".

**Impact.** On the permissive reading, write-capable reviewers can mutate source, and that only shows up afterwards through the baseline comparison. On the strict reading, codex-review cannot produce a review. In plan-review-loop, line 110's "report review incomplete" leaves the state at `phase: review`. Nothing says whether to cancel the loop, so the stop hook (`hooks/stop-hook.sh:125-139`) blocks twice and then fails open, which abandons the loop. The skill should own that outcome rather than leave it to the anti-trap path.

**Fix.** State one condition: the backend is usable only if the host can restrict each reviewer to read/search tools **and** capture its final message. Otherwise it is unavailable. Name a concrete way to satisfy it in Claude Code (a shipped `agents/inkstone-lane-reviewer.md` with `tools: Read, Glob, Grep`, or a named built-in read-only agent). In plan-review-loop, say what to do with the state file when no backend qualifies: log it, tell the user, and run `cancel` (or set a terminal phase). Don't rely on the hook's block budget.

### [medium] PID-based watcher and exit-status check assume one persistent shell, but the workflow spreads launch, probe and kill across separate tool calls
**Where:** `skills/codex-review/reviewer-backends.md:256-272`, `skills/codex-review/reviewer-backends.md:325-329` (success requires "exits successfully"), `skills/plan-review-loop/SKILL.md:94-108` · **Lane:** correctness

**Defect.** The new guidance replaces `pgrep -f` with `REVIEW_PID=$!`, `kill -0` and `wait`, and says to "keep its watcher in that same shell". plan-review-loop now captures `REVIEW_PID=$!` in the launch snippet (lines 95-97). Its liveness probe (~90 s later), its watchdog (5-minute/15-minute polling) and its "kill the process" steps are described as later, separate actions (lines 100-108). The text does not say how `REVIEW_PID` reaches them, and `wait` works only on a child of the current shell. The success criterion "exits successfully" also cannot be checked once the launching shell has gone.

**Impact.** If an agent follows the text across separate Bash tool invocations (the natural way to do a "probe at ~90 s" step), `REVIEW_PID` is empty or stale, so `kill -0 ""` fails and the watcher exits at once. `wait` then returns 127, which looks like a reviewer failure. Or the agent cannot kill a hung run without falling back to the `pgrep -f` pattern the doc now forbids. A good review can be rejected, or a hung one left running. I could not confirm whether this host's Bash tool keeps shell variables between calls (see limitations). The instructions should not depend on it either way.

**Fix.** Persist both values to files the caller owns. Write the PID at launch, e.g. `echo $! > .claude/<backend>-review.pid`. Record the exit status with a wrapper: `( codex … ; echo $? > "$EXIT_FILE" ) > "$OUT" 2>&1 < /dev/null &`. Have the probe, watchdog and kill steps read those files instead of `$REVIEW_PID` and `wait`. Alternatively, say explicitly that launch plus watcher must run as a single backgrounded tool call, and give that combined snippet.

### [low] plan-review-loop now hard-depends on a sibling skill's file with no fallback
**Where:** `skills/plan-review-loop/SKILL.md:72-75`, `:109`, `:110` · **Lane:** contracts & call sites

**Defect.** Backends 2 and 3 are specified only by reference to `reviewer-backends.md` in the `codex-review` skill directory ("prepare and inspect the report-scoped agent from…", "restricted tools and host output capture specified in…", "If the host cannot enforce the shared contract, report review incomplete"). Skills are discoverable and installable individually under the Agent Skills layout that AGENTS.md says this repo targets. If plan-review-loop is installed without codex-review, the opencode config and the subagent rules cannot be found.

**Impact.** In that setup only Codex remains usable. Without Codex, the review is reported incomplete and the hook fail-open path described in the first finding applies.

**Fix.** Either declare the dependency (README/AGENTS and the skill text: "requires codex-review installed alongside"), or add a short instruction: if the file cannot be found, log it and treat backends 2 and 3 as unavailable, then follow the same cancel/terminal-state handling.

### [low] Stop-hook confirm-phase instructions do not match the new confirmation contract
**Where:** `hooks/stop-hook.sh:182-184` vs `skills/plan-review-loop/SKILL.md:151` · **Lane:** contracts

**Defect.** The skill now requires the confirmation reviewer to get a fresh, separate artifact path with write access scoped to it, and the caller validates that output before appending `## Confirmation`. The hook's block reason, which is what a resumed or compacted session actually sees, still says only "Dispatch ONE fresh context-blind reviewer with the revised plan and the prior review file… Append its verdict". It does not mention the separate artifact or validation.

**Impact.** An agent driven by the hook text can hand the reviewer the original review path as its output. That violates the shared "reject an existing output file" rule (`reviewer-backends.md:309-311`). For opencode, it also means granting edit access to the file that holds the caller's `## Disposition`.

**Fix.** Add one clause to step 1 of the hook message: "write to a fresh separate confirmation file; validate it, then append its verdict". Re-run the hook path tests that AGENTS.md lists for the confirm block.
